

# **UAV Post-Flight Backend — Product Requirements Document (PRD v1)**

**Project:** UAV Post-Flight Analysis System
**Backend PRD Version:** v1.0
**Frontend Dependency:** UAV Dashboard PRD v2 (Frozen)
**Primary Goal:** Transform Pixhawk flight logs into structured mission analytics consumable by the React dashboard.

---

# 1. Executive Summary

The backend is a **mission ingestion and processing engine** responsible for converting UAV flight data into structured analytics for visualization.

The system:

* Connects to a Pixhawk flight controller running ArduPilot
* Downloads post-flight logs using MAVLink
* Processes `.BIN` logs locally
* Generates normalized mission JSON
* Serves REST endpoints consumed by the dashboard

The backend owns **all flight intelligence**.

The frontend is a visualization layer only.

---

## Core Principle

> Backend performs computation.
> Frontend performs presentation.

# 5. Mission Lifecycle State Machine

Frontend relies on this strictly.

## States

| State         | Meaning              |
| ------------- | -------------------- |
| `idle`        | Waiting for flight   |
| `downloading` | Log retrieval active |
| `parsing`     | Log processing       |
| `ready`       | Mission available    |
| `error`       | Processing failed    |

---

## State Transition Flow

```
idle
 ↓ (DISARM detected)
downloading
 ↓ (log saved)
parsing
 ↓ (JSON generated)
ready
```

---

## Requirements

* State must be thread-safe
* Only backend may modify state
* API endpoint is read-only

---

# 6. Data Pipeline

## Step 1 — Mission Detection

Backend listens for MAVLink HEARTBEAT.

Trigger condition:

```
armed == False AFTER being True
```

This indicates landing.

---

## Step 2 — Log Download

Backend sends:

```
LOG_REQUEST_LIST
LOG_REQUEST_DATA
```

Output:

```
storage/logs/<mission_id>.bin
```

---

## Step 3 — Parsing

Parser extracts:

| Category        | MAVLink Source |
| --------------- | -------------- |
| Attitude        | ATT            |
| Battery         | BAT            |
| Altitude        | BARO / CTUN    |
| Speed           | CTUN           |
| System Messages | STATUSTEXT     |
| Arming state    | HEARTBEAT      |

(GPS optional — may be absent.)

---

## Step 4 — Metrics Computation

Backend computes:

* flight duration
* max altitude
* max speed
* battery consumption
* peak current
* mission status

---

## Step 5 — JSON Generation

Produces schema EXACTLY matching frontend contract.

Stored as:

```
storage/missions/<mission_id>.json
```

# 8. API Specification (MANDATORY)

Frontend already depends on these.

---

## 8.1 `/api/mission/state`

Returns lifecycle state.

Polled every 2 seconds.

Must respond <50ms.

---

## 8.2 `/api/health`

Provides diagnostics:

* backend status
* last mission timestamp
* log size
* parse duration

---

## 8.3 `/api/mission/latest`

Returns latest processed mission JSON.

Must read cached file only.

Never parse on request.

---

## 8.4 `/api/mission/list`

Lists stored missions.

Generated by scanning `missions/` directory.

---

## 8.5 `/api/mission/:id`

Returns specific mission JSON.

---

## 8.6 Download Endpoints

Serve files directly:

* raw `.BIN`
* processed JSON
* metadata sizes

---

## 8.7 Payload Serving

Static file hosting:

```
/payload/<image>
```

---

# 9. Execution Model

## Background Worker Architecture

FastAPI must NOT handle MAVLink directly.

Instead:

```
FastAPI Startup
      ↓
Spawn Background Worker
      ↓
Worker runs pipeline
```

Worker responsibilities:

* MAVLink listening
* state updates
* downloading
* parsing

API only reads results.

* 50k+ data points

# 11. Error Handling

System must recover from:

* MAVLink disconnect
* partial downloads
* corrupt logs
* parser failure

On error:

```
state = error
message = human-readable explanation
```

Frontend displays retry UI.
